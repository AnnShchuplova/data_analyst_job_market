### ПМИ-1 🔴 Несуществующее поле в тесте `test_clean_experience`

**Место:** ПМИ, раздел «Тест-кейс TC-3: Очистка данных об опыте работы», ожидаемый результат.

**Проблема:**  
ПМИ утверждает, что после вызова `DataCleaner.clean_experience()` датафрейм должен содержать
колонку `estimated_experience_years`. В реальном коде (`src/data_processing/cleaner.py:148–162`)
эта функция создаёт только `min_experience_years` и `avg_experience_years`.
Поле `estimated_experience_years` генерирует `FeatureEngineer` (слой ML-признаков),
а не `DataCleaner` (слой очистки). Тест `tests/test_modules.py:112` проверяет именно DataCleaner
и поэтому **падает** с `AssertionError`.

**Готовый текст для замены:**

```
TC-3. Очистка данных об опыте работы

Тестируемый компонент: DataCleaner.clean_experience()
Файл: src/data_processing/cleaner.py

Входные данные:
    DataFrame с колонкой «experience», содержащей словари вида
    {"id": "between1And3", "name": "От 1 года до 3 лет"}.

Ожидаемые результаты:
    После выполнения метода датафрейм должен содержать следующие колонки:
      • experience_id   — строковый идентификатор категории опыта (напр., "between1And3")
      • experience_name — человекочитаемое название категории (напр., "От 1 года до 3 лет")
      • min_experience_years — минимальное число лет опыта (целое: 0, 1, 3, 6)
      • avg_experience_years — среднее число лет опыта по диапазону (целое: 0, 2, 4, 8)

Примечание:
    Поле estimated_experience_years НЕ является результатом DataCleaner.
    Оно создаётся позднее — классом FeatureEngineer (src/data_processing/feature_engineering.py)
    на этапе подготовки ML-признаков. Тестировать его следует в тест-кейсах для FeatureEngineer,
    а не для DataCleaner.

Критерий прохождения:
    assertIn("experience_id", cleaned.columns)
    assertIn("experience_name", cleaned.columns)
    assertIn("min_experience_years", cleaned.columns)
    assertIn("avg_experience_years", cleaned.columns)
```

ПМИ перечисляет только `id`, `title`, `avg_salary`, `skills`, `remote_rate` — пять из десяти.
Неполный список вводит в заблуждение при ревью результатов теста.

**Готовый текст для замены:**

```
TC-5. Кластеризация вакансий

Тестируемый компонент: ClusteringService.perform_clustering()
Файл: src/services/clustering_service.py

Ожидаемый результат:
    Метод возвращает объект ClusteringResult со следующими атрибутами:
      • method_name      — название алгоритма ("K-Means", "K-Modes" или "K-Prototypes")

      • salary_rate      — доля вакансий с указанной ЗП (float, 0–100)
      • skills           — список из ≤5 самых частых навыков
      • remote_rate      — доля удалённых вакансий (float, 0–100)

### РП-3 🟡 Неверное описание инвалидации кэша / перезагрузки сервисов

**Место:** РП, раздел «5. Кэширование», описание механизма обновления данных.

**Проблема:**  
Инвалидация кэша в проекте работает через MD5-checksum последнего CSV-файла,
вычисляемый `VacanciesRepository.compute_checksum()`. Декоратор `@st.cache_resource`
в `clusters.py:33` и `home.py:7` принимает checksum как аргумент-ключ —
при смене файла checksum меняется и сервис пересоздаётся автоматически.
Если в РП описан иной механизм (ручной перезапуск, `st.cache_data.clear()` вручную и т.д.),
это устаревшая информация.

**Готовый текст для замены:**

```
5. Механизм инвалидации кэша

Веб-контейнер обнаруживает новый CSV-файл в finaldata/ без перезапуска сервера.

Алгоритм:
  1. @st.cache_data(ttl=300) функция get_checksum() (clusters.py:47, home.py:14)
     раз в 5 минут вычисляет MD5-хэш последнего по времени модификации CSV-файла
     через VacanciesRepository().compute_checksum().
  2. Хэш передаётся аргументом в @st.cache_resource-функцию get_service(data_checksum).
  3. Пока хэш не меняется — Streamlit возвращает закешированный сервис.
     Как только parser-контейнер записал новый CSV и хэш изменился —
     сервис пересоздаётся (новый DataFrame, новый ClusteringService / HomeService).
  4. Кэш кластеризации (ClusteringCache, joblib) использует составной ключ:
     MD5(version | checksum | features | k_range).
     При смене checksum старые результаты кластеризации автоматически не подходят.

Ручная инвалидация: кнопка «Обновить статистику» на главной странице вызывает
_get_checksum.clear() и _get_service.clear() (home.py:91–92), принудительно
сбрасывая оба кэша.
```

### РО-2 🟡 Не задокументировано ограничение по числу вакансий при парсинге

**Место:** РО, раздел «2. Сбор данных / Запуск парсера».

**Проблема:**  
`src/data_collection/hh_parser.py:60` содержит параметр `pages: int = 20`.
При стандартном размере страницы hh.ru API = 100 вакансий это даёт не более 2 000 вакансий
за один сеанс парсинга. Оператор не знает об этом лимите и может ожидать полную
выгрузку (десятки тысяч вакансий).

**Готовый текст для замены:**

```
2.4. Ограничения сбора данных

Парсер собирает не более 2 000 вакансий за один запуск (20 страниц × 100 вакансий/страница).
Это ограничение задано параметром pages=20 в классе HHParser
(файл src/data_collection/hh_parser.py).

При необходимости получить более широкую выборку:
  • Запустите парсер несколько раз с разными параметрами фильтрации (регион, дата);
  • Или увеличьте параметр pages в коде (рекомендуется не превышать 50 во избежание
    блокировки по rate-limit со стороны hh.ru API).

Дубликаты между запусками удаляются автоматически скриптом scripts/merde_databases.py.
```

```
4.2. Требования к кластеризации

  • Алгоритм выбирается автоматически по типу входных признаков:
    - только числовые  → K-Means (евклидова метрика)
    - только категор.  → K-Modes (расстояние Хэмминга, инициализация Cao)
    - смешанные        → K-Prototypes (расстояние Gower)

  • Название кластера формируется из профессий с долей ≥ 30% вакансий в группе.
  • Метка уровня зарплаты:
    🟢 высокая — медианная ЗП кластера выше 70-го перцентиля рынка

### ПЗ-1 🟡 MockService описывается как активный компонент

**Место:** ПЗ, раздел «5. Архитектурные решения» / «Сервисный слой».

**Проблема:**  
`src/services/mock.py` содержит `MockService` — заглушку, созданную на раннем этапе разработки.
В `app/main.py:100` экземпляр `MockService()` создаётся и передаётся в `view_home` и
`view_salary_predictor`, но оба view-модуля принимают аргумент и не используют его.

`ClusterEntity(1, "ML Engineers", ...)` с 6 позиционными аргументами,
тогда как `ClusterEntity` сейчас имеет 10 полей — вызов упал бы с `TypeError`.
MockService — мёртвый код, не используемый в production-пути.

**Готовый текст для замены:**

```
5.4. MockService (legacy-компонент)

src/services/mock.py содержит класс MockService — заглушку, созданную для разработки
без реальных данных. В текущей версии приложения MockService НЕ используется
ни в одном активном пути исполнения.

Экземпляр MockService создаётся в app/main.py и передаётся в view_home / view_salary_predictor,
однако оба модуля читают данные самостоятельно через VacanciesRepository и игнорируют аргумент.

Статус: legacy / deprecated. Файл сохранён для совместимости с тестовой инфраструктурой.
При следующем рефакторинге рекомендуется удалить src/services/mock.py и аргументы service=
из сигнатур view-функций, не использующих его.
```

### ПЗ-2 🔵 Не описана дублирующаяся функция `_load_data()` в четырёх view-модулях

**Место:** ПЗ, раздел «5. Архитектурные решения», описание слоя доступа к данным.

**Проблема:**  
ПЗ описывает `VacanciesRepository` как единственный слой доступа к данным.
На практике функция `_load_data()` (читает последний CSV из `finaldata/`) продублирована
в четырёх модулях: `clusters.py`, `predict_salary.py`, `arima.py`, `aggregation.py`.
`VacanciesRepository` используется только в `home.py` и `clusters.py` (через checksum).

**Готовый текст для замены:**

```
5.3. Доступ к данным

Основной класс доступа к данным: VacanciesRepository (src/infrastructure/vacancies_repository.py).
Методы:
  • load_latest()        — загружает самый свежий CSV из finaldata/ в DataFrame
  • compute_checksum()   — вычисляет MD5 последнего CSV (используется для инвалидации кэша)

Текущее состояние (версия 1.0):
  VacanciesRepository напрямую используется в home.py и clusters.py.
  Модули aggregation.py, predict_salary.py и arima.py содержат локальную функцию _load_data()
  с аналогичной логикой (загрузка последнего по mtime файла из finaldata/).
  Это технический долг: дублирование не нарушает корректность, но усложняет сопровождение.
  В будущих версиях все четыре модуля должны использовать VacanciesRepository.load_latest().
```
