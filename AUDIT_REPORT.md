## 🔴 Критические ошибки

### КО-1 — Тест падает на несуществующем поле `estimated_experience_years`

| | |
|---|---|
| **Файл (код)** | `tests/test_modules.py:113` |
| **Файл (документ)** | Тищенко_ПМИ.pdf, раздел «Тестирование модуля DataCleaner» |
| **Симптом** | `TestCleaner.test_clean_experience` завершается с `AssertionError` |

**Детали:**

```python
# tests/test_modules.py:110–114
cleaned = cleaner.clean_experience(df)
self.assertIn("experience_id", cleaned.columns)
self.assertIn("experience_name", cleaned.columns)
self.assertIn("estimated_experience_years", cleaned.columns)  # ← ПАДАЕТ
```

`DataCleaner.clean_experience()` (`src/data_processing/cleaner.py:124–172`) создаёт поля:
- `experience_id`
- `experience_name`
- `min_experience_years`
- `avg_experience_years`

Поля `estimated_experience_years` в этом методе **нет**. Оно генерируется классом
`FeatureEngineer` (`src/data_processing/feature_engineering.py`) как производная фича,
а не в DataCleaner.

**Расхождение с ПМИ:** документ декларирует, что все юнит-тесты проходят успешно.
Фактически этот тест **не проходит**.

**Исправление:** заменить `"estimated_experience_years"` на `"min_experience_years"`
или `"avg_experience_years"` в `tests/test_modules.py:113`.

### КО-2 — Баг в блоке «Что стоит выучить?» (рекомендации навыков)

| | |
|---|---|
| **Файл (код)** | `app/views/aggregation.py:1272–1273` |
| **Файл (документ)** | Тищенко_ТЗ.pdf, раздел «Мой профиль — рекомендации навыков» |
| **Симптом** | Пользователю показываются навыки с НАИМЕНЬШИМ приростом зарплаты |

**Детали:**

```python
# app/views/aggregation.py:1271–1273
top_candidates = sorted(
    candidates.items(), key=lambda x: x[1]["bonus"], reverse=False  # ← ascending!
)[:15]
```

`reverse=False` + `[:15]` → берём 15 навыков с **минимальным** бонусом.
Требование ТЗ: отображать навыки, которые **максимально** повышают зарплату.

**Исправление:**

```python
top_candidates = sorted(
    candidates.items(), key=lambda x: x[1]["bonus"], reverse=True
)[:15]
```

### КО-3 — Захардкоженная дата обрезки в продакшн-пути SARIMA

| | |
|---|---|
| **Файл (код)** | `app/views/arima.py:413` |
| **Файл (документ)** | Тищенко_РО.pdf, раздел «Работа с модулем трендов» |
| **Симптом** | Все данные позже 5 апреля 2026 молча отбрасываются при просмотре прогноза |

**Детали:**

```python
# app/views/arima.py:412–414
ts = analyzer.prepare_time_series(
    df, freq="D", end_date="2026-04-05"   # ← захардкоженная дата!
)
```

При каждом запросе вкладки «Прогноз SARIMA» временной ряд обрезается по фиксированной дате.
По мере роста датасета всё больше реальных данных будет отброшено без предупреждения.
В обучающей вкладке (`arima.py:529`) комментарий объясняет причину:
`"Данные обрезаются до 5 апреля 2026 (далее были проблемы со сбором)"` —
но в продакшн-пути этого комментария нет и пользователь не информирован.

**Расхождение с РО:** руководство оператора не описывает это ограничение.

**Исправление:** убрать `end_date` или вынести дату в конфиг с явным предупреждением в UI.

## 🔵 Белые пятна

### БП-1 — Нет валидации схемы CSV при загрузке

| | |
|---|---|
| **Файл (код)** | `src/infrastructure/vacancies_repository.py:36–46` |

`load_latest()` загружает любой CSV без проверки обязательных колонок.
Если парсер запишет файл с другой схемой — web-сервис упадёт с `KeyError` в runtime.
Минимальная защита — проверить наличие `['salary_avg', 'published_at', 'area_name']`
сразу после чтения.

---

### БП-2 — Нет версионирования обученных моделей

| | |
|---|---|
| **Файл (код)** | `app/views/predict_salary.py:360` |

```python
predictor.save(model_path)  # перезаписывает models/salary_predictor.pkl
_load_model.clear()
```

Каждое переобучение перезаписывает единственный файл модели.
При неудачном обучении (R² < порог) предыдущая рабочая модель теряется без возможности отката.
Решение: хранить модели с временной меткой, оставляя N последних.

### БП-3 — Streamlit-приложение открыто без аутентификации

| | |
|---|---|
| **Файл (код)** | `docker-compose.yml:22` (порт 8501:8501) |

Приложение слушает `0.0.0.0:8501` без какой-либо защиты.
Документы не указывают, что это сознательное решение для внутреннего использования.

### БП-4 — Поведение SARIMA при разреженных данных не задокументировано

| | |
|---|---|
| **Файл (код)** | `src/ml/arima_analyzer.py` |

Сезонный период `m` определяется автоматически по частоте (D→7, W→52, ME→12).
Для корректной оценки сезонной компоненты требуется минимум `2×m` точек.
При сборе менее 14 дней данных (для частоты D) модель может выдать
ненадёжный прогноз без предупреждения в UI.
